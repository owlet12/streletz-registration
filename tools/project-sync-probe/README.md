# Проверка передачи проекта через фактический Windows EXE

Этот runner использует собранный производственный `StreletzBridge.exe` для
.NET Framework 4.8. Он не включает исходники моста повторно и не использует
ветку `BRIDGE_CORE_TESTS` с System.Text.Json.

Через reflection создаются `RegistrationCoordinator` и `LanReceiver` из EXE.
`ReceiveOnce` слушает только `127.0.0.1`; защищённые запросы и ответы проходят
настоящий TCP-приёмник, ProtocolV3 и JavaScriptSerializer. Главная форма,
Master, native pipe и оборудование не запускаются. Подставной драйвер считает
любой вызов ошибкой, отдельно проверяются отсутствие записи журнала,
результатов регистрации и каталога панелей.

Проверяются большой полный проект из 453 записей, небольшой `notModified`,
повторная загрузка после изменения содержания, отказ при другом коде
подключения, отсутствие проекта и превышение лимита. Проверка лимита использует
многобайтовый текст. Содержимое проекта и ключи не печатаются.

Для VPN защищённый запрос отправляется двумя фрагментами с паузой 9 секунд,
превышающей прежний тайм-аут Windows в 7 секунд. Проверяются успешный полный
ответ, исходный requestId и ровно один вызов обработчика без повторной
отправки. Это настоящий локальный TCP-сценарий, а не проверка значения
константы. Аппаратный тайм-аут регистрации и допустимый возраст запроса
остаются отдельными ограничениями.

Отдельно проверяется диагностический ответ через тот же сериализатор и
ProtocolV3: состояние отсутствующего/некорректного ID, источник сведений,
полный ID записи МК-IP в проекте и результаты дополнительных проверок
штатного маршрута. Значение ID из проекта не подставляется в отсутствующий
ID строки подключения. Логические значения `false` сохраняются; строки,
числа и `null` не принимаются за результаты проверок. Произвольный текст,
полные строки подключения и секреты исключаются.

Сначала соберите мост, затем runner:

```powershell
dotnet build source/windows-bridge/build.csproj -c Release
dotnet build source/tools/project-sync-probe/probe.csproj -c Release
source/tools/project-sync-probe/bin/Release/net48/ProjectSyncProbe.exe source/android/app/src/main/assets/project.json source/windows-bridge/bin/Release/net48/StreletzBridge.exe
```

Runner сравнивает SHA256 загруженного EXE с указанным аргументом и печатает
его версию. На Linux для запуска используется Mono 6.8 с библиотеками
System.Web.Extensions и System.Windows.Forms. Проверка не заменяет запуск на
реальном Windows/Android и не проверяет конкретный пользовательский BFX.

## Восстановление операции · 0.5.9

Дополнительный сценарий использует настоящий Windows EXE и его
`PanelRegistrationDriver` с подставным локальным native-транспортом.
Проверяются отсутствующая история, выполняющаяся операция и подтверждённый
сохранённый результат. Все пять идентификаторов и реальные логические
значения `true`/`false` проходят сериализатор .NET Framework и защищённый
TCP-ответ. Чужой проект отклоняется до native-чтения. Восстановленный
результат сохраняется в журнал и проект; повторное чтение не запускает
операцию. Любой вызов native `start` или `cancel` немедленно проваливает
этот сценарий.

Исходный native-отпечаток намеренно отличается от текущего, как при
штатном изменении записи после регистрации. Остальные исходные
идентификаторы и маршрут остаются точными. Проверка не открывает
GUI Master и не подключается к оборудованию.

## ИБ1-ПРО и новая копия проекта · 0.5.9

Реальный конвертер BFX из EXE читает синтетическую запись обычного ИБ1-ПРО
128:98 и её панель. Проверяются поля устройства и полный ID, отказ
от смешивания с подтипом 95, сохранение заполненных данных по GUID,
исторический отпечаток операции и атомарное создание новой копии.
Существующий файл не может быть перезаписан этой командой; входные данные
и прежняя копия остаются неизменными.
