# Дополнение Master 1.0.9.0 / комплект 0.5.20

Добавлена обработка точного вопроса о тайм-ауте готовности ДУ: один ответ Нет, без повтора, с неизвестным физическим результатом. Обновите также Windows-мост до 0.5.20; APK 0.5.17 прежний. Подробности: README.md комплекта и docs/VERIFICATION_0.5.20.md.

## История и устройство модуля

# Дополнение регистрации для «Стрелец-Мастер» 12.4

Текущее исправление **1.0.8.0**, комплект **0.5.19**: корректное разделение физического интерфейса МК-IP и маршрута через Панель-Терминал. После сохранения проекта закройте Master, замените DLL и перезапустите Master. Последующие описания выпусков 1.0.7 и ранее являются историей.

`Plugin.StreletzRegistration.dll` — обычное дополнение Master. Оно принимает локальные запросы Windows-моста, находит выбранную запись в **уже открытом проекте Master**, запускает штатную команду `InitDevice` и управляет её штатным диалогом по типам, идентификаторам и полям проверенной версии. Подключение к МК-IP, проверка доступа, обмен с панелью и подтверждение регистрации выполняются кодом Master.

Дополнение предназначено для одного открытого экземпляра Master в интерактивном сеансе Windows. Windows-мост должен работать под тем же пользователем и в том же сеансе. Плагин не запускает Master, не открывает проект, не вводит пароль пользователя программы и не подменяет проектную конфигурацию соединения.

## Установка

1. До замены DLL проверьте незавершённые операции в работающем Master и старом мосте, завершите либо отмените активную регистрацию и сохраните достоверный результат. Память операций дополнения не переносится после перезапуска Master: новая DLL не сможет восстановить прежний `operationId` по своей памяти. После проверки закройте Master перед установкой DLL.
2. Соберите дополнение с `Core.dll` из исследованного официального дистрибутива 12.4. Из папки `master-plugin`:

   ```powershell
   dotnet build .\Plugin.StreletzRegistration.csproj -c Release -p:MasterInstallDir="C:\Путь\к\Стрелец-Мастер"
   ```

3. Поместите **только** полученную `bin\Release\net48\Plugin.StreletzRegistration.dll` в каталог с `Master.exe` и `Core.dll`. Библиотеки изготовителя остаются установленными штатным способом; они не включаются в дополнение.
4. Запустите Master, откройте рабочий `.bf` / `.bfx` и войдите обычным способом. Проверьте, что выбранное соединение проекта относится к нужному МК-IP.
5. Запустите Windows-мост под этим же пользователем. Его проверка `hello` должна вернуть `ready:true`; `list_panels` — нужный МК-IP, адрес соединения и GUID панели.

В комплекте 0.5.10 используется DLL с версией файла **1.0.7.0**. При обновлении замените также эту DLL и перезапустите Master после проверки прежних операций: каталог ИБ 1-ПРО, проверка физического TCP-подключения и принадлежности маршрута выполняются самим дополнением. Обновления только Windows-моста для поддержки ИБ 1-ПРО недостаточно. Ответ `hello` содержит `pluginVersion: "1.0.7.0"`; версия сборки остаётся `1.0.0.0`.

Загрузчик Master ищет именно **`Plugin.*.dll`** в каталоге, содержащем `Core.dll`: `Core.Common.BaseDirectory.GetPath()` возвращает каталог этой сборки, с резервным переходом к `AppDomain.CurrentDomain.BaseDirectory`. В проверенной штатной установке это общий каталог с `Master.exe`, а не отдельная папка `Plugins`. Загрузчик исключает пути, содержащие `XmlSerializers`. Имя файла дополнения соответствует нужной маске.

Для запуска Master, дополнения и производственной сборки `StreletzBridge.exe` необходим **.NET Framework 4.8**. Устанавливать runtime .NET 8 не требуется: .NET SDK 8 использован только для компиляции и отдельных тестов. Запуск выполняется от одного обычного пользователя Windows в одном интерактивном сеансе. Если каталог установленной программы защищён Windows, копирование DLL в него может потребовать прав администратора; постоянно запускать Master или мост с такими правами не требуется.

### Проверяемая версия

`VersionGuard.cs` содержит SHA-256 пятнадцати исследованных компонентов официального дистрибутива 12.4, включая `Argus.GUI.Common.dll`, где находятся штатные UI-диспетчер и `MasterProgrammer`, и `BaseAdapterTransport.dll`, где выбирается физический транспорт. Версия сборки `Core.dll` — `12.4.33.0`. Если хотя бы один компонент отличается, операции регистрации не разрешаются; `hello` возвращает `unsupported_master_build`. Изменение строки версии или отключение проверки не является способом поддержки другой сборки: для другой сборки необходимо проверить API, контроли и токены заново. Дополнительно проверяются конкретные штатные типы `FormManager` и `MasterProgrammer`; контекст с удалённым `CommandExecutorChannel` отклоняется.

Сборка исходников — отдельная проверка от испытания на Windows с Master и панелью. В ходе подготовки выпуска 0.5.9 программа Master и команды оборудования не запускались. Официальный URI-конвертер, встроенный каталог устройств и читающие свойства синтетических объектов информации из DLL изготовителя исполнялись отдельно без GUI и открытия соединений; проверка метаданных и IL отдельно выполнялась без исполнения команд изготовителя. Первая проверка полного маршрута должна выполняться на установленной проверенной версии Master с нужным проектом и конкретным устройством.

## Работа регистрации

Планируемая последовательность: выбрать запись и её основную панель на телефоне → запросить регистрацию → дождаться состояния ожидания датчика → выполнить физическую активацию PROG → дополнение выбирает только обнаруженную строку с точным ожидаемым аппаратным ID → штатный обработчик Master подтверждает её с KEY из проектной записи → Master проверяет результат → телефон получает подтверждённую регистрацию.

Плагин не выбирает первую строку списка и не подтверждает другой ID. Записи экспортированного проекта сохраняют GUID из `Item.@id`; по этому GUID выполняется поиск в живом дереве Master. Для данного экспорта разрешены типы `(128,0)`, `(128,17)`, `(128,32)`, `(128,77)`, `(128,94)` и ИБ 1-ПРО `(128,98)`. Для добавленного ИБ 1-ПРО дополнительно требуется точный штатный класс информации `StreletcPro.IB1.Info` из проверенной сборки `Plugin.StreletcPro`.

Проверяются принадлежность записи основной панели и сегменту, проектный узел МК-IP, его аппаратный ID, адрес и порт. Поддержаны прямой МК-IP и МК-IP парной Панели-Терминала. Перед подтверждением дополнительно проверяется фактически открытый адаптер штатного диалога. Облачные, USB и произвольные межсегментные маршруты этим вариантом дополнения не обслуживаются. Если невозможно однозначно доказать соответствие, подтверждение не выполняется.

KEY можно передать как восемь шестнадцатеричных символов или оставить пустым для штатного значения записи. KEY не возвращается через IPC и не записывается в журнал дополнения. Значение в проекте, изменённое только для ещё не отправленного запроса, подлежит восстановлению при отмене; после отправки аппаратного подтверждения автоматический откат не должен изображать отмену выполненной регистрации.

`registrationConfirmed:true` означает, что наблюдался штатный `InitDu.Successfully` и у той же живой записи проверен ожидаемый аппаратный ID. `projectSaved` всегда `false`: сохранение проекта и последующее программирование конфигурации выполняются отдельно штатными средствами Master. Плагин не считает редактирование переносимого JSON подтверждением аппаратной регистрации.

Если подтверждение уже отправлено, а достоверный итог получить не удалось, состояние — `unknown`. Повторный запрос с новым `operationId` в такой ситуации создавать не следует: сначала проверьте состояние той же операции и результат в Master. Отмена после успешного завершения не переводит зарегистрированный датчик в незарегистрированный.

## Завершение без итогового сообщения · 0.5.10

В версии 1.0.6.0 попытка автоматически подтвердить штатное сообщение могла закончиться общим success_acknowledgement_timeout, который скрывал последнюю проверку. Отчёт пользователя подтвердил такую блокировку при уже доказанной регистрации; конкретный не прошедший HWND-признак по старому отчёту определить нельзя.

Версия 1.0.7.0 использует отдельный экземпляр NativeInitDeviceCommand, унаследованный от проверенного штатного InitDevice. Он сохраняет Key/Guid/ApplyMaintenance зарегистрированного образца и не изменяет сам образец. Только тело ProcessCommand выполняется с SilentMode=true; переопределённый виртуальный PreCommandCheck с четырьмя аргументами выполняет штатные проверки с SilentMode=false и возвращает их результат/исключение без изменения. finally восстанавливает режим на каждой границе. Подтверждённый IL двухаргументного precheck действительно вызывает четырёхаргументный слот виртуально. Вызов базового ProcessCommand выполняется невиртуально во избежание рекурсии.

Штатный InitDevice передаёт !SilentMode в четвёртый аргумент InitDu. Его private readonly Boolean-поле 04000040 читается на реально созданной форме до выбора датчика; оно должно иметь значение false. Присваивания этому полю, переписывания изготовительских DLL и перерегистрации глобальной команды нет. Если режим не установлен или экземпляр команды не может сохраняться из-за удалённого CommandExecutor, выдаётся native_result_mode_unavailable до подтверждения регистрации. RunType не переопределяется.

Сам InitDu выполняет обнаружение и регистрацию. В успешной ветви он устанавливает Successfully, возвращает результат 2 и штатно закрывает собственную форму. Полный ID, переданный KEY, принадлежность записи и маршрут проверяются существующим обработчиком; FormClosed позволяет наблюдать успех до возвращения Programmer.Run. NativeRunFinished и dialogClosed отражают только фактическое завершение. Отключение итогового сообщения не является доказательством регистрации.

Режим также пропускает необязательную печать этикетки в успешной ветви команды с телефона. Ошибки и вопрос повторного поиска остаются штатными и не получают автоматического подтверждения. Ручные команды Мастера не изменяются.

hello.capabilities.suppressNativeSuccessDialog=true сообщает о возможности загруженной DLL. nativeSuccessDialogSuppressed=true выставляется только после проверки поля созданной формы. nativeCompletionLastCheck сохраняет последнюю содержательную проверку при общем тайм-ауте. В режиме без сообщения используются awaiting_native_completion и native_completion_timeout; реальное завершение становится completed/native_completion_finished. Старый проверяемый обработчик OK сохранён, но при подтверждённом флаге подавления оконные API не вызываются.

Новое задание до фактического завершения предыдущего получает native_result_closing либо native_result_acknowledgement_blocked. Это отказ до новой аппаратной регистрации. Уже открытый диалог прежнего процесса 1.0.6.0 нельзя изменить обновлением APK: новый режим применяется после замены DLL и перезапуска Мастера.

Проверки текущего выпуска — docs/VERIFICATION.md: собственный режим проверен на синтетическом BaseCommand, реальный штатный IL и слоты вызовов — отдельным vendor-success probe без GUI и аппаратных команд. Пользовательский Windows GUI и панель в среде сборки недоступны.

## Прямое подключение без облачного SerialNumber · 0.5.8

В штатной ветви генерации прямого соединения Master 12.4 добавляет `AdapterConnectionDto.SerialNumber` только при включённом облачном канале. Это поле выбирает модуль для облачного транспорта; при отключённом облаке корректная строка прямого подключения может содержать GUID узла МК-IP, IP и порт, но не содержать `SerialNumber`. Проверка 0.5.7 ошибочно считала такое отсутствие несовпадением модуля.

В 0.5.8 полностью указанный ID по-прежнему сравнивается со всеми шестью байтами проектного ID. Чужой, сокращённый, недопустимый или нулевой ID отклоняется. Только действительно отсутствующий параметр допускает дополнительную проверку: текущий узел МК-IP должен оставаться тем же объектом проекта и сетевым интерфейсом нужного сегмента; его полный ID обязан совпасть с запросом; прямое подключение должно быть включено, а облачное — выключено. Строка фактически открытого соединения должна точно совпасть с уже созданной и сохранённой в сегменте штатной строкой, а её хеш пароля — с текущим проектным значением. Проверки реального авторизованного TCP-соединения, GUID владельца, IP, порта, принадлежности записи и результата регистрации сохранены.

Чтение использует проверенное приватное поле `adapterNameValue`; публичный getter `AdapterName` не вызывается, потому что он может заново создавать строку и открывать диалоги конфигурации. Сброшенный или изменившийся кэш, изменённый пароль и неизвестные настройки дают отказ. Для Панели-Терминала эта же проверка относится к физической строке `StartPointAdapterName` парного терминального сегмента; внешний владелец основной панели и ММПИ проверяются отдельно.

В диагностике `actualModuleIdState` различает `present`, `missing` и `invalid`. `moduleIdentitySource` обозначает `endpoint_and_project` либо `project_adapter_and_native_route`; `projectModuleId` сохраняется отдельно. При отсутствии ID в открытой строке `actualModuleId` остаётся пустым — проектное значение не выдаётся за прочитанный из соединения ID. Флаги `nativeRouteCacheMatched`, `nativeCloudEnabled`, `nativeDirectEnabled`, `nativeRoutePasswordMatched` появляются только после соответствующих проверок. Строка подключения и хеш пароля в отчёт не передаются.

Тест транспорта и чтения проектного маршрута содержит **71 проверку**, включая запрет вызова публичного getter и раскрытия секретов. Отдельный тест с реальным конвертером и читающими свойствами информации изготовителя содержит **41 проверку** на синтетических данных: канонический полный ID, отсутствие облачного параметра, точный кэш, настройки сегмента, изменение полного ID и пароля. Физическая регистрация на пользовательском оборудовании этими тестами не выполняется.

## Исправление принадлежности адаптера · 0.5.7

Физический `UsbProxyAdapter.SegmentGuid` в исследованном Master 12.4 не заполняется путём создания и открытия соединения. Это изменяемая служебная подсказка маршрутизации событий; сравнение её с GUID сегмента датчика ошибочно отклоняло правильное соединение с `adapter_segment_mismatch`.

Теперь прямой маршрут доказывается через `AdapterUrlConverter.AdapterOwnerGuid`: штатный генератор URI берёт его из `OwnerGUID` выбранного узла МК-IP. Декодированный GUID обязан совпасть с `op.AdapterNodeId`, установленным по живому проекту. Пустой GUID и чужой узел с тем же IP, портом и аппаратным ID отклоняются. Дополнение не записывает значение в служебное поле `SegmentGuid`. Фактический TCP-транспорт, полные ID, принадлежность датчика панели, отпечаток проекта и состояние штатного окна продолжают проверяться.

Терминальный маршрут содержит два разных владельца. Физическая строка `TunnelDto.StartPointAdapterName` принадлежит узлу МК-IP терминального сегмента. Внешняя строка `GetInterfaceName()` принадлежит основной панели и содержит сериализованные ММПИ `from`/`to`. Свойства `StartPointSegment`, `EndPointSegment` и `StartPointAdapterName` помечены изготовителем `JsonIgnore`, поэтому их проверка выполняется по readonly-полю фактического адаптера; ожидать их в десериализованной внешней строке нельзя. Внешний владелец и оба адреса ММПИ проверяются отдельно. Ни один из этих путей не заменяет основной контроллер терминалом.

В диагностике раздельно указаны `expectedAdapterNodeId`/`actualAdapterOwnerId` и `expectedRouteOwnerId`/`actualRouteOwnerId`. Сырые URI и их пароли не экспортируются. `source/tools/vendor-adapter-owner-probe` вызывает официальный конвертер и производственные методы проверки DLL на синтетических строках: правильный маршрут с незаданной подсказкой сегмента принимается, чужой/пустой владелец, неверный IP/порт/ID и ММПИ отклоняются. Полный UI и аппаратная регистрация этими проверками не воспроизводятся.

## Исправление проверки МК-IP · 0.5.6

В 0.5.5 проверка ошибочно отклоняла параметр `ForceUsbScheme:true`. В официальном `MkIpInfo.GetConnectionParams()` этот параметр выставляется всегда: он означает формат обмена МК-IP и применяется также при соединении по TCP. В штатной фабрике при указанном IP создаётся `WebPort`, обёрнутый в `CryptoUsb` и `UsbWrapper`. Наличие этого флага не доказывает подключение физическим USB-кабелем. Поэтому корректная регистрация могла остановиться на шаге `native_adapter_mismatch` после обнаружения нужного датчика.

В 0.5.6 формат протокола отделён от доказательства фактически выбранного транспорта. Чтение выполняется по точным типам и полям проверенной сборки: `EthernetUSB` → внутренний `Transport` → `TransportHolder.nestedTransport` → `TransportCollaborator.currentTransport` → криптографическая обёртка → `WebPort`. Проверяются признак завершённой штатной криптографической авторизации, readonly-URI и удалённый адрес уже соединённого TCP-сокета. IP и порт должны совпасть с выбранным МК-IP. Полный шестибайтный ID остаётся обязательным; сокращённый серийный номер USB не заменяет его. Дерево проекта, GUID панели, сегмент, принадлежность записи и маршрут терминала проверяются прежним способом.

Штатный Master перебирает транспорт в порядке USB → DirectIP → облако. Наличие USB-порта в настройках ещё не означает, что выбран именно он. Если фактически выбран `HidDeviceTransport` или `CloudProxy`, дополнение возвращает отдельную причину `transport_usb` или `transport_cloud`. Изменение формата протокола не разрешает эти маршруты.

Чтение доказательств не вызывает `Open`, `IsOpen`, `Read`, `Write`, `Cancel` или `Close`. Это существенно: в исследованном коде getter `WebPort.IsOpen` может проверять сокет нулевой отправкой и закрывать неактивное соединение. Вместо него читаются поля и адрес уже открытого сокета. Состояние `Socket.Connected` является сохранённым состоянием последней операции и само по себе не доказывает успешную регистрацию; подтверждение по `InitDu.Successfully` и ID записи остаётся отдельным обязательным шагом.

Ответ операции содержит `adapterDiagnostic`: код конкретной проверки, тип активного транспорта, ожидаемые и прочитанные IP/порт/ID, GUID сегментов и признак формата `forceUsbScheme`. Сырые URI, пароли, ключи, тексты исключений и внутренние проектные объекты в этот объект не входят. При чтении неизвестного типа или изменившегося транспорта подтверждение останавливается.

## Маршрут через Панель-Терминал · 0.5.5

Основная панель остаётся владельцем датчика. МК-IP терминала задаёт физическое соединение; он не становится новой панелью-владельцем записи.

В штатном объекте сегмента `CorePlugins.segment.CustomInfo` читается `IsViaPanel3DuplicateEnabled`. При включённом флаге дополнение вызывает `GetDuplicatePair()` у контроллера основной панели. В исследованном Master 12.4 этот метод находит сегмент с номером **основной + 30 в той же системе**, затем требует у его контроллера `PanelMode.Duplicate`. Обратная связь терминала должна указывать на тот же объект основной панели. Повторяющиеся номера сегментов, другая система, неправильный режим контроллера, отсутствие ММПИ или неустановленный МК-IP дают неподтверждённый маршрут. Названия и положение строк дерева не используются как связь.

Для основной панели сегмента 2 выбирается терминал сегмента 32, для панели сегмента 3 — терминал сегмента 33. Нативный `panelId` и `nativeNodeGuid` обозначают основную панель; `segmentGuid` обозначает её сегмент. Значения `host`, `port`, `moduleId`, `adapterNodeId` и `adapterSegmentId` берутся из МК-IP терминального сегмента. `terminalPanelId`, `terminalSegmentId` и `terminalDisplayName` описывают терминал отдельно. `displayName` читается из штатного `CustomTreeNode.Text`, чтобы на телефоне отображался номер и название из дерева Master.

Значения `routeKind`: `direct_mk_ip` или `panel_terminal`. Запрос терминальной регистрации обязан передать все GUID маршрута и `viaPanelTerminal:true`. Старые запросы без этих полей могут обслуживать только прямое подключение. Изменение терминала или адаптера отклоняется даже при неизменном IP-адресе. Фактические адреса ММПИ обоих сегментов включены во внутренний отпечаток; они не передаются в журнал операции.

Штатный `ApplicationManager.GetAdapter` использует режим `AdapterFromDuplicate`. Дополнение не открывает самостоятельное соединение и не меняет сетевой интерфейс проекта. В штатном диалоге читается `LockedAdapter.GetUnderlyingAdapter()` и фактический `EthernetUSB`. У проверенной сборки readonly-поле `UsbProxyAdapter` с токеном `0x040000DB` содержит `TunnelDto`, переданный фабрикой: сравниваются оба GUID сегментов и оба адреса ММПИ. Его `StartPointAdapterName` проверяется штатным `AdapterUrlConverter`: должны совпасть проектный GUID узла МК-IP, прямой IP и порт; полный ID связывается с проектом по правилам раздела 0.5.8 выше. Внешний `GetInterfaceName()` проверяется как туннельная строка с GUID основной панели и точными ММПИ `from`/`to`; сегменты и физический адрес проверяются по readonly-объекту, поскольку в JSON они не сериализуются. Пароли из URI не экспортируются.

Если у основной панели также настроен собственный адаптер, Master может сначала установить связь через него. Если фактически открытый путь отличается от выбранного терминального маршрута, дополнение остановит подтверждение. Для конфигурации со скриншота пользователя — сетевой интерфейс основной панели не установлен, флаг подключения через терминал включён — Master сам переходит к парному терминалу.

Метаданные и маршрутизация исследованы по официальным файлам 12.4, а не по именам, предположенным из скриншота. Реальный BFX объекта и регистрация на оборудовании в этом окружении не проверялись.

## Локальный IPC

Имя канала:

```text
StreletzMasterBridgeV1-<Windows SessionId>
```

Одна UTF-8 строка JSON на подключение, одна строка ответа. Максимум запроса — 32 KiB. Максимум ответа — **4 MiB UTF-8 вместе с переводом строки**. Сериализатор ответа отделён от сериализатора запроса; большой каталог не ограничивается прежними 32 768 символами. Если ответ не помещается или не сериализуется, модуль возвращает короткую ошибку вместо закрытия канала без ответа. DACL разрешает доступ текущему SID Windows и `LocalSystem`, запрещает `NETWORK`; дополнительно установлен `PIPE_REJECT_REMOTE_CLIENTS`. Первое создание канала требует `FILE_FLAG_FIRST_PIPE_INSTANCE`. Сетевой телефон напрямую к каналу не обращается: проверкой сопряжения телефона занимается Windows-мост.

Общий ответ:

```json
{"ok":true,"protocol":"streletz-master-plugin-v1","data":{}}
```

Ошибка:

```json
{"ok":false,"protocol":"streletz-master-plugin-v1","error":{"code":"panel_mismatch","message":"..."}}
```

Запросы: `hello`, `list_panels`, `start`, `status`, `cancel`. Для `status` и `cancel` необходим `operationId`.

```json
{
  "type":"start",
  "operationId":"unique-operation-id",
  "projectFingerprint":"fingerprint-of-phone-export",
  "nativeProjectFingerprint":"value-from-native-list-panels",
  "recordId":"native-record-guid",
  "expectedHardwareId":"0123456789AB",
  "deviceKey":"",
  "timeoutSeconds":120,
  "panel":{
    "host":"192.168.0.240",
    "port":6344,
    "moduleId":"0123456789AB",
    "panelId":"windows-bridge-profile-id",
    "nativePanelId":"native-panel-guid"
  }
}
```

`panelId` — ID профиля Windows-моста; его не следует подставлять вместо GUID панели. `nativePanelId` берётся из `list_panels`. Экспортный и нативный отпечатки обозначают разные представления проекта. Для строгой проверки изменения живого дерева передавайте `nativeProjectFingerprint`, полученный непосредственно перед запуском. Даже без него обязательна точная проверка записи и её настроенного МК-IP.

При повторе **идентичного** `start` с тем же `operationId` возвращается существующая операция. Конфликт содержимого с уже использованным ID отклоняется. Пока предыдущий native workflow или его диалог открыт, другая операция не запускается.

`native_ui_busy` означает, что очередь UI была снята до начала выполнения. `native_outcome_unknown` означает, что обработка началась и истёк срок ожидания ответа; требуется `status` с прежним ID. Состояния операции: `queued`, `connecting`, `waiting_sensor`, `detected`, `registering`, `registered`, `cancelled`, `failed`, `unknown`.

Ответ операции содержит исходные `projectFingerprint`, `panelId`, `nativePanelId`, `host`, `port`, `moduleId` и `recordId` для сопоставления с запросом. Дополнительно возвращается проверенная идентичность маршрута: `routeKind`, `viaPanelTerminal`, `terminalPanelId`, `terminalSegmentId`, `adapterNodeId`, `adapterSegmentId`. Windows-мост сверяет её перед применением результата. `nativeDialogOpen` и `dialogClosed` обновляются в UI-потоке; подтверждённая остановка до отправки регистрации требует одновременно `nativeRunFinished:true`, `dialogClosed:true`, `confirmationSent:false`. Хранятся 128 полных результатов; ID вытесненных операций остаются занятыми до завершения процесса Master и не могут запустить операцию повторно.

## Диагностика связи

Windows-мост различает отсутствие ответа при подключении к каналу, отказ Windows в доступе, тайм-аут ответа уже открытого канала, обрыв ответа, неверный протокол, требование открыть проект или войти в него и несовпадение проверенной сборки. Один тайм-аут не доказывает отсутствие DLL: модуль может быть ещё не загружен, находиться в другом сеансе или обслуживать другой запрос.

Окно «Диагностика связи» показывает результат последней проверки и позволяет сохранить его в текстовый файл. Отчёт содержит время, этап, код, PID/сеансы, видимость DLL рядом с обнаруженным `Master.exe` и при наличии — имя компонента, не прошедшего проверку сборки. Сырые запросы, ответы, исключения, конфигурация, пароли, PIN и KEY датчиков в отчёт не попадают. Сохранение отчёта не выполняет новое подключение и не запускает регистрацию.

Жизненный цикл дополнения сохранён: после `Initialize` оно ждёт главную форму `Master.Main`, затем запускает канал; завершение основной формы или приложения останавливает канал. Проверка пятнадцати файлов и ограничения доступа к каналу не отключались.

## Тест большого ответа

```powershell
dotnet build .\native-json-tests.csproj -c Release
.\bin\native-json-tests\net48\NativeReplyJson.SelfTest.exe
```

Тест использует настоящий `System.Web.Script.Serialization.JavaScriptSerializer`: воспроизводит отказ старого ограничения на синтетических каталогах 453 и 445 записей, проверяет полный перенос после исправления, предел UTF-8 и сохранение прежнего ограничения запроса. Здесь он выполнен под Mono 6.8: **13 проверок пройдены**. Запуск Master, Windows UI и оборудования этим тестом не проверяется.

## Проверки терминального маршрута

`native-route-tests.csproj` проверяет 36 условий привязки: две разные пары панель/терминал, несовпадение системы, неоднозначные номера, смену узла при том же IP, обязательные GUID, оба конца фактического туннеля, совместимость прежнего прямого запроса и отсутствие KEY в ответе. Прогон под Mono 6.8 прошёл; UI и оборудование не запускались.

`source/tools/vendor-terminal-route-probe` отдельно читает PE-метаданные официальных DLL, без загрузки и исполнения кода изготовителя. К проверкам маршрута терминала добавлены поля фактического транспорта, их точные типы и признаки readonly, а также IL-доказательство безусловной установки `ForceUsbScheme:true` в `MkIpInfo.GetConnectionParams()`.

## Проверки физического транспорта

`native-transport-tests.csproj` проверяет производственный код чтения доказательств на контролируемой структуре объектов и настоящем локальном TCP-соединении `127.0.0.1`. Проверяются корректный TCP с форматом МК-IP, реально выбранные USB и облако, смена IP/порта, отсутствие авторизации или выбранного транспорта, закрытый сокет, неизвестный тип, неполный ID и отсутствие секретов в JSON. Специальные ловушки подтверждают, что производственная проверка не вызывает транспортные методы и `IsOpen`.

Эта проверка не запускает Master, не подключается к пользовательской панели и не проверяет физическую регистрацию. Реальный BFX объекта, Windows UI, драйверы USB и оборудование требуют отдельной проверки на компьютере пользователя. Логи прогона включены в каталог `docs` комплекта.
